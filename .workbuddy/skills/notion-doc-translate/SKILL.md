# Notion 文档翻译流程

## 适用场景

用户要求翻译或更新 `notion-docs-tracker` 项目里某篇（或某批）Notion 帮助文档的中文译文。

**不适用**：同步逻辑、抓取逻辑、状态回填（见 `scripts/audit-status.ts` / `scripts/apply-status.ts`）。

## 背景

- 英文源：`content/<identifier>.md`（如 `content/help:notion-ai-app-for-ios.md`），标准 Markdown + frontmatter，**CRLF/LF 混排**
- 中文译文：Notion Frontend 数据源的页面正文
- 关联方式：`Identifier` 属性（`help:<slug>`）
- 术语：`translation/glossary.md`（权威）
- 规范：`translation/style-guide.md`（权威）

**不保存任何本地状态。** 没有翻译快照、没有审计日志。每篇按单次处理，判断"英文改了什么"靠 `content/` 的 git 历史。

## 硬规则

1. **只用定点替换，禁止整页重写。** 页面里可能有 `<unknown .../>` 这类无法转换的块，`replace_content` 会直接删掉它们。
2. **不改结构。** 标题层级、列表项数、表格行列、代码块数量必须与英文一致。
3. **不动页面顶部 `<callout>`。** 那是 `Description` 属性的投影。
4. **不改 URL。** 内部链接保留英文原地址——见「链接策略」。已有的 `/p/` 内部链接不要反向改回英文。
5. **不改 `Status` 属性。** 用户自己改，不要碰。
6. **UI 标签以 Notion 自身为准，不强求统一。** 例如 `AI Meeting Notes` 在中文界面里可能写作 `会议记录`，与正文的「AI 速记」并存是正常的，因为 Notion 自己的翻译就不一致。**不要"修正"这类不一致。**
7. **术语以 `translation/glossary.md` 为准。** 表里没有的高频词先问，不要自己造。
8. **链接左侧是汉字时必须留半角空格。** `切换到[新体系](url)` 是错的，要写成 `切换到 [新体系](url)`。右侧紧跟汉字同理。英文源里链接左边天然带空格，压缩成中文后最容易丢——见 `translation/style-guide.md` 第四节「链接两侧的空格」。
9. **必须汇报。** 不要自称「已完成」，要让用户能校验。

## 流程

### 第 1 步：生成工作包

```bash
bun run translate:context help:some-doc
```

产物在 `.cache/translate/<slug>.md`，包含：

| 小节 | 用途 |
| --- | --- |
| 元信息 | 页面 ID、状态、字数、markdown 保真度 |
| **英文源最近改动（git）** | 最近一次真正改正文的提交和 diff。已过滤 frontmatter 与标题锚点噪声 |
| 标题对齐表 | 英中标题按序号配对，数量不一致会告警 |
| **链接清单** | 英文 help 链接（待用户改）与内部 `/p/` 链接（已转好，核对目标） |
| 术语表 / 翻译规范 | 全文 |
| 英文源 / 中文现状 | 全文 |

### 第 2 步：判断到底要改什么

- **用户指定了改哪句** → 直接改那一句，不用管别的。
- **用户只说"更新一下这篇"** → 看「英文源最近改动（git）」，那是英文最近一次真实改动，对照中文看是否已覆盖；没覆盖的就补。
- **英文没变** → 用户大概是让校对，跑下面「交付前自动检查」找问题。

**不要**用段落行数比英中差异。Notion 的 `{toggle="true"}`、Tab 缩进、`<unknown/>` 会让中文行数天然偏多，比出来全是假差异。

### 第 3 步：产出 patches

写到 `.cache/translate/<slug>.patches.json`：

```json
{
  "identifier": "help:some-doc",
  "patches": [
    {
      "old_str": "页面里现有的中文原文，必须唯一命中",
      "new_str": "替换后的中文",
      "note": "一句话说明为什么改"
    }
  ]
}
```

`old_str` 取法：

- 从工作包「中文现状」整行/整段复制，**不要手敲**
- 太短会命中多处，往上多带一行上下文
- 列表项要带上 `- ` 前缀

### 第 4 步：dry-run

```bash
bun run translate:apply -- --file .cache/translate/<slug>.patches.json
```

校验 `old_str` 唯一命中。报错就回去修 patches，不要绕过。

### 第 5 步：写入

```bash
bun run translate:apply -- --file .cache/translate/<slug>.patches.json --apply
```

脚本会复核、比对结构指标、保存英文源快照、写审计日志。

结构指标报警时判断是否预期：**新增链接导致 `links` 递增是正常的**，其他指标变化要回头查是哪个 patch 引起的。

## 交付前自动检查

**每篇交付前都跑，翻译和校对一视同仁。** 只在校对时跑是不够的——新译出来的段落一样会漏。这些能抓出大部分机械错误，跑完再动手改。

| 检查 | 做法 | 能抓到什么 |
| --- | --- | --- |
| URL 集合比对 | 逐节提取 `](url)`，比英中集合 | 漏掉的链接。**注意**：中文若已把英文链接转成 `/p/`，集合必然不同，要人工判断 |
| 列表项数量 | 数 `^[-*] ` 和 `^\d+\. ` | 漏译的列表项 |
| 标题层级 | 比每级标题的 `#` 数量 | 层级漂移 |
| 数字比对 | 提取纯数字，排除 URL 里的（`%E2%80%99` 会误报） | 漏掉的数字 |
| 引号扫描 | 数 `“`/`”` 是否配对，查 `「」` | 引号错乱、折角引号残留 |
| 标题格式 | 查标题内 `**`、结尾句号 | 格式污染 |
| **翻译腔扫描** | 剔除固定词（可以/以及/以下/以上/以内/**以外**/以前/以后/所以/予以/难以/足以/以便/用以/得以）和 `以…为准` 句式中残留的 `以`；另查「进行+动名词」「做出+名词」「这允许你」「需要注意的是」 | 「XXX 以 XXX」等直译腔。**注意 `当…时` 不是问题**，别误伤 |
| **链接空格** | 正则 `[\u4e00-\u9fff]\[` 和 `\)[\u4e00-\u9fff]`，命中即漏 | 中文紧贴链接。**每条翻译都要扫，不是只在校对时扫** |
| 口语化 | 扫「吼」「咱」「啦」「呗」「哈」「呀」「哦」「嘛」 | 语气不符合帮助文档 |

## 链接策略

**新译或新写的链接：保留英文原地址。**

```
✅ https://www.notion.com/help/account-settings
❌ /p/328e8a5565ac81f1b039e85b627e1bbb?pvs=25
```

原因：中文目标页可能尚未创建、内容未更新，或锚点对应的标题不存在。自动映射会产生死链，比语言不对更糟。

**用户会自己把英文链接转成 Notion 内部链接。** 所以：

- 我保留英文，**在汇报里全列出来**，他在维护时统一改。
- **已有的 `/p/` 内部链接不要动**，也不要反向改回英文——那是他之前花时间做的，改回去是倒退。

工作包的「链接清单」已经把两类分好了，直接抄进汇报。

## 汇报格式（强制）

**无论改了多少处，这个格式都必须完整输出。** 哪怕只改了一个词，也要把清单走一遍——把「无」写出来，而不是省略整节。

````markdown
## 改了什么

- `help:xxx`（N 处）
  1. 第 X 段：原「…」→ 新「…」，因为英文源这里新增了…
  2. …

## ⚠️ 需要你手动处理

### 链接

| # | 链接文字 | 锚点 | 目标 | 出现在 |
| --- | --- | --- | --- | --- |
| 1 | 账号设置 | 有 | `help:account-settings` | …如果你忘了密码… |

（没有就写「无」）

### 术语

| 英文 | 我用的译法 | 需要你确认 |
| --- | --- | --- |
| deploy | 部署 | 术语表没覆盖，按通用译法 |

（没有就写「无」）

### 结构

- 英文 47 个标题 / 中文 47 个，层级全部一致
- 或：第 7/12/13 个标题英文是 h4、中文是 h3，要不要改？

（没有就写「无」）

### 原文存疑

- 第二段英文自相矛盾：前面说 3 个方案，后面列了 4 个。我按 4 个译的。

（没有就写「无」）

### 我没能处理

- 目标页还没建，链接没法给中文地址
- 没有逐字校对全文，只做了定向检查，建议重点看 X 和 Y 两节

（没有就写「无」）

## 校验方式

打开 <Notion 链接>，重点看上述位置。
````

### 汇报的几条硬要求

- **不许只说「已完成」。** 用户要自己校验，必须告诉他具体看哪里。
- **不许隐瞒问题。** 拿不准的地方、按自己判断处理的地方，都要写出来。
- **链接清单一律全列。**
- 用户通常只需要改一两处，但**问题清单不能因为改动小就简化**。
- 坦白说明检查覆盖到什么程度。做了定向检查就说清是哪几项，不要暗示"全文校对过"。

## 批量处理

1. `bun run translate:context help:a help:b help:c` 一次生成
2. 逐篇读、逐篇产出 patches
3. 每篇单独 dry-run + apply，**不要攒着一起写**
4. 每篇单独出汇报，最后给汇总（成功 / 跳过 / 待用户处理）

中途某篇失败就跳过并记下，不要因为一篇卡住整批。

## 踩过的坑

**`grep` 在工作包上失效。** 工作包含超长行（1700+ 字符），`grep` 判定为二进制，`grep -n` 静默返回空。改用 `python3` 或 `Read` 工具。

**段落行数比对是废信号。** Notion 结构标记让中文行数天然偏多，比出来全是假差异。

**`truncated: true` 不是长度截断。** 它和 `unknown_block_ids` 相关，表示有无法转换的块，不代表内容被砍。不影响定点替换，但**绝对不能**改用 `replace_content`。

**英文源 CRLF 混排。** 336/337 个文件含 `\r`，按 `\n` 切行会让标题正则失效（标题数会少一半）。脚本已归一化，手工处理时要留意。

**`old_str` 找不到。** 页面实际文本跟工作包不一致（用户刚手动改过）。重跑 context 拿最新的。

**`old_str` 多次命中。** 加上前后文。中文「点击继续」这种短句很容易重复。

**中文紧贴链接是最容易漏的错误。** 英文源里是 `move to the [new credit system](...)`，左边有空格；照抄 `old_str` 后压缩成中文，就变成「切换到[新的积分体系](...)」，读起来不刺眼，但用户会当成错误退回来。**每译完一篇就扫 `[\u4e00-\u9fff]\[`，不要等到最后。**

**标题文本匹配要脱掉井号。** `blocks.children.list` 返回的 `plain_text` 不含 `###`，拿 `### xxx` 去匹配标题永远 0 命中。

**按文本删块必须打印命中内容再删。** 用 `children.slice(-N)` 猜位置会删错真正文（踩过一次，删掉了 FAQ 最后一段）。精确匹配 `plain_text`，命中数不符预期就中止。
